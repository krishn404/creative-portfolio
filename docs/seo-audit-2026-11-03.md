# KTWK SEO audit and implementation report

Audit date: 2026-11-03  
Canonical origin: `https://art.krixnx.xyz`  
Canonical series name: **Kezual Talks w Kant (KTWK)**  
Recognized search variation: **KWTK**

## Baseline

The site is a Next.js 16 App Router application deployed on Vercel. Public content is rendered as static or incrementally regenerated HTML. Convex is the content store, Cloudinary serves article covers, and Vercel Analytics is present. KTWK articles use `/blog/[slug]`; topics use `/blog/tag/[tag]`; the main archive is `/blog`; the series explainer is `/about-ktwk`.

The live sitemap contained 57 URLs: eight article URLs, four primary/static URLs, and 45 topic/tag URLs. All eight sitemap article URLs returned 200, exposed an H1, a canonical, crawlable links, article content, and BlogPosting JSON-LD. The live blog archive linked to the published articles with ordinary HTML anchors. HTTP redirects to HTTPS and the non-`www` origin is the canonical host.

The repository already had several useful SEO pieces: dynamic article metadata, canonical URLs, Open Graph and Twitter cards, robots and sitemap routes, an RSS feed, BlogPosting and breadcrumb JSON-LD, previous-slug redirects, server-rendered article content, article navigation, related posts, an admin SEO panel, and a Google verification file at `public/googleaa7f108a2836fd29.html`. That verification file was preserved unchanged.

The local `.env` Convex deployment is not the same content environment used by the live Vercel site. It returned two published records, including `/blog/kayze-renaissance-album-story`, while the live site has eight posts and uses `/blog/renaissance-album-review-by-Kayze`. Validation must therefore use the deployment's production Convex environment when checking production content.

No authenticated Search Console API or connector was available. Live indexing, queries, impressions, clicks, CTR, and Google-selected canonicals were not claimed or inspected.

## Prioritized findings

### P0 — critical

- No currently deployed sitemap article was blocked or noindexed; all eight resolved successfully.
- Environment mismatch is a release risk: the local Convex content set differs from production. A build made against the wrong deployment can prerender and validate the wrong article set.

### P1 — high impact

- Article titles were forcibly shortened and then followed by a long repeated brand suffix. Several live titles ended in an ellipsis before the brand. The generation logic now preserves the real headline and uses the concise `| KTWK` suffix.
- Custom descriptions were passed through a generic expansion routine, producing doubled punctuation, boilerplate, or mid-thought truncation. Custom descriptions are now preserved and clamped at a word boundary; generated fallbacks use only the real excerpt/title plus a short KTWK attribution.
- The homepage emitted FAQPage data for questions not visibly presented on the page. Article FAQPage data was also emitted generically. Both were removed; visible FAQ copy remains available to readers without unsupported rich-result markup.
- Every tag/keyword produced an indexable one-sentence archive and a sitemap URL. Most live tag archives contained one article, creating 45 low-value archive URLs. Topic pages now become indexable and enter the sitemap only when they contain at least two published posts; one-post pages remain accessible with `noindex,follow`.
- `/admin` was blocked in robots.txt but inherited indexable metadata. Admin routes now explicitly emit `noindex,nofollow`.
- `/cd-player`, `/test`, `/play-ground`, and `/play-ground/grid` lacked page-specific canonical handling. They now have unique titles, descriptions, canonicals, social metadata, and appropriate sitemap entries.
- The homepage had no H1 in rendered HTML. It now has one semantic H1 without changing the visible design.

### P2 — content, structure, and performance

- Sitemap `lastmod` values for static pages changed on every generation even when content had not changed. Unverifiable dates were removed; article and writing dates still come from actual `updatedAt`/`publishedAt` data.
- BlogPosting schema now includes real guest names when explicitly stored, word count, free-access status, an image array, accurate dates, and Home → KTWK → article breadcrumbs.
- The visible article byline now shows a genuine updated date when it is meaningfully later than publication.
- The editor now warns about title-only excerpts, incomplete guest names, vague cover alt text, and missing inline-image alt text. Inline article images receive lazy loading.
- The live validator found missing alt text on two images in BLUK, three in Hadi, two in Vidhu Kota, and two in Rohh. These require factual descriptions from the editor; they were not invented automatically.
- Cloudinary cover URLs already request automatic format/quality and fixed 1200×675 or 1200×630 dimensions. The article cover has explicit dimensions and priority. No speculative visual or animation changes were made.
- Google PageSpeed Insights returned quota-exceeded responses for both mobile and desktop, so no lab score is claimed. Search Console field Core Web Vitals and a fresh Lighthouse run remain post-deployment checks.

### P3 — optional

- Dedicated artist landing pages are not justified yet because most artists have one article and no stored biography. The article page is the primary artist-search target. Create `/blog/artist/[slug]` only after an artist has multiple related interviews or verified, distinct profile copy.
- The `www.art.krixnx.xyz` HTTPS hostname currently presents a certificate-name mismatch before the application redirect can run. Fix the domain/certificate in Vercel or DNS only if `www` is intended to be supported; the canonical non-`www` host works.
- The repository-wide lint baseline has unrelated existing React/compiler errors. Changed SEO files are clean; `components/profilecard.tsx` still has an existing effect lint error, although its TypeScript icon types were corrected.

## Search query strategy

- **KTWK** is the canonical abbreviation and is used in article title suffixes, archive copy, navigation, and structured data.
- **KWTK** is represented as a legitimate search variation in site keywords, series aliases, structured data, and visible explanatory copy. It is not used as the primary brand name.
- **Kezual Talks w Kant** and **Kezual Talks with Kant** are represented through the canonical name and alternate names.
- Explicit `guestName` is the authoritative artist entity. It feeds article keywords and Person relationships in BlogPosting data.
- Article H1s, excerpts, real topics, related links, and tag links support `[Artist] interview`, `[Artist] KTWK`, and `[Artist] Kezual Talks with Kant` without inserting unsupported claims.
- One-post artist tags are not used as thin indexable landing pages; the full interview remains the canonical search target.

## Automated validation

Run:

```text
pnpm test
pnpm exec tsc --noEmit --pretty false --incremental false
pnpm run build
pnpm seo:validate
```

For a local production server, pass its URL:

```text
pnpm seo:validate -- http://127.0.0.1:3100
```

The validator checks robots/sitemap agreement, sitemap response status, blog-to-sitemap article coverage, article status, canonical URLs, indexability, one H1, unique titles and descriptions, JSON-LD syntax, required BlogPosting fields, body depth, and missing image alt text.

Final local results: eight unit tests passed; TypeScript passed; the production build passed; the local rendered SEO validation passed with zero errors and zero warnings. The current live validation passed with zero errors and nine missing-alt warnings across four articles. Full-project ESLint still fails on pre-existing non-SEO code.

## Google Search Console deployment checklist

1. Deploy with the production `NEXT_PUBLIC_CONVEX_URL` and `NEXT_PUBLIC_SITE_URL=https://art.krixnx.xyz`.
2. Run `pnpm seo:validate` against the deployed site.
3. Confirm `https://art.krixnx.xyz/googleaa7f108a2836fd29.html` still returns the existing verification text.
4. In URL Inspection, run a live test for `/`, `/blog`, `/about-ktwk`, and at least one old and one newest interview. Confirm successful fetch, allowed indexing, rendered article text, the declared canonical, and Article structured data.
5. In Sitemaps, submit or resubmit `https://art.krixnx.xyz/sitemap.xml`; confirm `Success` and monitor discovered versus indexed article URLs.
6. Request indexing for the blog archive and the most important updated interviews. Do not use Google's Indexing API for these ordinary articles.
7. In Page indexing, review `Crawled - currently not indexed`, `Discovered - currently not indexed`, duplicate/canonical, soft-404, and blocked results.
8. In Performance, create filters for `KTWK`, `KWTK`, `Kezual Talks`, each artist name, `/blog`, and individual article pages. Export the pre-deployment comparison period.
9. In Core Web Vitals, review mobile and desktop URL groups; run Lighthouse/PageSpeed again for the homepage, archive, and a cover-heavy interview.

Official references: [Article structured data](https://developers.google.com/search/docs/appearance/structured-data/article), [structured-data quality guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [title guidance](https://developers.google.com/search/docs/appearance/title-link), [meta description guidance](https://developers.google.com/search/docs/appearance/snippet), [sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), [URL Inspection](https://support.google.com/webmasters/answer/9012289), and [Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals).

## Future publishing workflow

1. Create the post in the existing admin editor.
2. Use the complete public headline as the post title; add a shorter SEO title only when the preview is too long.
3. Set the stable lowercase slug before first publication. If it changes later, the existing redirect system records the previous slug.
4. Add a specific excerpt and meta description based only on the article.
5. For interviews, enter the artist's verified display name in `guestName` and add only real topics to tags/keywords.
6. Upload a cover and describe the actual image. Add descriptive alt text to every meaningful inline image.
7. Write a factual 40–60 word summary and add FAQ copy only when it helps readers; FAQ text no longer creates unsupported rich-result schema.
8. Review all SEO warnings, publish, and verify the new URL appears in `/blog`, `/sitemap.xml`, RSS, relevant multi-post topics, structured data, and related links.
9. Run `pnpm seo:validate` after deployment and inspect the new URL in Search Console.

## 30/60/90-day monitoring

- Save a baseline on deployment day: sitemap article count, indexed article count, clicks, impressions, CTR, average position, query/page exports, and mobile/desktop Core Web Vitals.
- At 30 days, verify every submitted article's indexing state; compare brand queries (`KTWK`, `KWTK`, full series name), artist queries, clicks, CTR, and top landing pages against the baseline. Fix coverage or snippet mismatches before rewriting content.
- At 60 days, compare equal-length periods, identify articles earning impressions but low CTR, refine only factual titles/descriptions, and strengthen internal links from relevant articles. Review whether any artist now qualifies for a useful multi-interview landing page.
- At 90 days, compare the full 90-day period with the prior 90 days where available; segment brand, artist, and non-brand discovery queries; review indexed count, clicks, CTR, position distribution, and Core Web Vitals. Preserve annotations for deployments and article edits so movement is not attributed blindly.

Search engines control crawling, canonical selection, indexing, snippets, and rankings. The implementation improves eligibility and clarity but does not guarantee a position or rich result.
